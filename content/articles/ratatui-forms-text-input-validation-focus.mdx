Terminal forms work when focus is obvious and validation is close to the field that needs attention. Widgets render controls; your app owns values, focus, and submit rules.

*By Max Wells, creator of [Rust/UI](https://rust-ui.com) and [Rustify](https://rustify.rs).*

> **TL;DR:** A production Ratatui form keeps values, focus, validation, and submission in app state while widgets render the current decision and feedback.
> - **Model focus explicitly** with an enum or state machine instead of scattered booleans
> - **Validate at a boundary** such as blur or submit, then return focus to the first invalid field
> - **Make errors actionable** and preserve the user input that caused them
> - **Test keyboard flow** for valid, invalid, disabled, and partially completed states


## Who should use this forms guide?

**This guide is for Rust engineers building terminal setup screens, search flows, configuration editors, or operational commands where invalid input must be recoverable.** It assumes widgets are already available and focuses on app-owned state, focus transitions, and validation policy.

A form is not a row of input boxes. It is a state machine: a user enters a value, moves focus, receives feedback, corrects the value, and submits or cancels. Making those transitions explicit keeps the UI predictable when fields become conditional or asynchronous.

## How should form state be modeled?

**Store each value, its validation state, and the focused field in one application model.** An enum makes focus transitions readable and avoids contradictory booleans such as two fields being active at once.

```rust
enum Field { Name, Email, Submit }

struct FormState {
    focus: Field,
    name: String,
    email: String,
    name_error: Option<String>,
    email_error: Option<String>,
    submitting: bool,
}
```

Keep validation output separate from raw input so an error does not erase what the user typed. If a field is disabled while a request runs, preserve its value and mark the state explicitly.

The [Text Input](/docs/widgets/text-input), [Text Area](/docs/widgets/text-area), and [Form Field](/docs/widgets/form-field) docs provide copyable controls. The article's job is to show how those controls fit into an app model.

## When should validation run?

**Validate at a clear boundary and explain the next action.** Validate on submit for forms where partial values are normal; validate on blur for fields where an early error prevents the next step. Avoid showing an error while the user is still typing a value that is temporarily incomplete.

An actionable message names the rule and the repair: “Email must contain @” is better than “Invalid.” Keep the input visible, return focus to the first invalid field, and leave valid fields untouched. For async validation, show pending state and prevent duplicate submission.

| State | Visible cue | Allowed action |
| --- | --- | --- |
| untouched | label only | type, move focus |
| focused | border or marker | edit, submit if allowed |
| invalid | error text plus marker | edit, retry |
| submitting | progress/status | wait or cancel |
| success | confirmation | continue or reset |

## How should keyboard focus work?

**Make focus order stable and visible without relying on color.** Tab moves forward, Shift+Tab moves backward, Enter submits or advances according to the form contract, and Escape cancels when cancellation is safe.

Map keys to actions in the event loop rather than handling raw key codes inside every field. This lets a mouse click, a shortcut, and a test call the same focus transition. Keep labels short, preserve the current value when focus changes, and provide a help hint for less common commands.

For larger forms, group fields into sections and use [Radio Card](/docs/widgets/radio-card), [Checkbox](/docs/widgets/checkbox), or [Select List](/docs/widgets/select-list) when a free-text field would create avoidable validation work.

## How do you test a form that changes state?

**Test transitions, not just the final screenshot.** Cover focus movement, typing, backspace, invalid submit, corrected input, disabled submit, and a successful result. Render the error and focused state with [TestBackend](/articles/test-ratatui-apps-testbackend) so the contract stays stable in CI.

Why this matters professionally: configuration and admin TUIs often run over SSH or in incident conditions. A form that makes recovery obvious saves more operator time than one with a polished happy path.

> **Bottom line**: Put state ownership and recovery rules in the app. Widgets should make those rules visible, not invent them.

## How should a form submit in a production workflow?

**Treat submission as a state transition with validation, in-flight, success, and failure states.** The submit action should snapshot the current values, disable duplicate requests, and preserve user input when the server rejects the request.

Keep field errors keyed by field identity, plus a form-level error for failures such as authorization or a network timeout. Ratatui widgets render the result; they do not replace the application validation model. After a successful save, clear only the state that should reset; an editor may keep its values while a create dialog closes. This distinction is easy to test when `submit()` returns an explicit app action rather than mutating widgets directly.

For a configuration form, validate cheap local rules immediately and defer remote uniqueness checks until submit or blur. Show the pending action in the form itself, not only in a global status bar. The user should know whether pressing Enter queued a request, succeeded, or failed and can be retried.

## What form mistakes create avoidable support work?

**The most damaging form mistakes hide focus, erase input on error, or make invalid values look accepted.** A red border without text is not enough for a keyboard user, and clearing the form after a timeout forces expensive re-entry over SSH.

Avoid one boolean per field for focus; an enum gives the form one legal focus target. Avoid validating only on submit when a field has an obvious local constraint such as an empty required value. Avoid allowing Enter to submit from a multiline editor unless the action is explicit. These rules should be documented in the help row and mirrored in tests.

Review forms with a screen reader-like discipline: can a user infer the label, current value, error, and next key without color? That review also improves screenshots and terminal recordings because the state remains legible in plain text.

> **Bottom line**: A form earns trust by preserving intent through validation and failure. Never make a user retype data because the network was slow.

## Why do production forms matter professionally?

**A terminal form is a compact demonstration of state modeling, validation, and failure recovery.** Those skills transfer directly to configuration tools, deployment consoles, and administrative workflows where a lost value can cost more time than a slow render.

A form that preserves input through server errors and exposes keyboard behavior gives reviewers a concrete signal: you can design a safe interaction under imperfect network and terminal conditions, not just draw controls.
## Frequently Asked Questions

### Should validation happen on every keystroke?

Only when immediate feedback helps and the rule is stable while typing. For emails, paths, and multi-step values, blur or submit validation usually avoids noisy errors. Keep the policy consistent across fields.

Validate cheap syntax while typing when it helps correction, but avoid showing a failure for an incomplete value. Run authoritative validation on submit and preserve the submitted values when a server response rejects them.

### How do I keep focus accessible without color?

Use a border, cursor, marker, or explicit “focused” label in addition to color. Test the focused state with a limited palette and a narrow rectangle so the cue remains visible.

Use a focus marker, label, and error text together. Color can reinforce the state, but the keyboard user must still know which field receives input and which key moves focus.

### Where should form values live?

Keep values in application state, not inside a widget wrapper. The app must be able to validate, submit, reset, persist, and test them independently of rendering.

Keep values in an app-owned struct and let widgets receive the current value. This makes reset, cancel, serialization, and TestBackend assertions deterministic instead of dependent on widget internals.

### How do I handle async submit?

Mark the form submitting, disable duplicate actions, send a request-owned message to the UI loop, and render success or error as state. Do not block the event loop while waiting.

On submit, move to an explicit pending state, disable duplicate activation, and keep input visible. A cancellation action should signal the worker and return the form to an editable state without losing values.

### Should Enter always submit?

Define it per form. In a multi-field form Enter may advance, while a final submit control or shortcut submits. Document the choice in the help hint and tests.

Enter should submit only when the focused control is a submit action or a single-line field with that documented behavior. In multiline input, use a separate shortcut so inserting a newline never triggers an irreversible request.

### What makes an error message useful?

It states the failed rule and the next repair, preserves the input, and moves focus to the first actionable field. Avoid generic errors that force the user to guess what changed.

An error should name the field, explain the constraint, and give the next correction. “Invalid value” is not actionable; “Port must be between 1 and 65535” is. Keep server and local errors visually distinct when both exist.
